<task type="auto">
  <name>Task 1: Fix global exception handler to preserve HTTPException status codes</name>
  <files>backend/app/main.py</files>
  <action>
The root cause of ALL three 500 errors is the `@app.exception_handler(Exception)` at line 65 of `main.py`. This handler catches `Exception`, which includes `HTTPException`. When `get_company_context` raises `HTTPException(403)` or `_require_admin_or_system_admin` raises `HTTPException(403)`, the global handler catches it and returns `JSONResponse(status_code=500)`.

**Fix the handler to re-raise HTTPExceptions so FastAPI's built-in handler processes them:**

Replace lines 65-77 in `backend/app/main.py`:

```python
@app.exception_handler(Exception)
async def global_exception_handler(request: Request, exc: Exception):
    # Let FastAPI's built-in handler deal with HTTPExceptions.
    # This preserves the correct status code (403, 404, etc.) and
    # ensures CORSMiddleware can add headers to the response.
    from fastapi import HTTPException
    if isinstance(exc, HTTPException):
        raise exc
    logger.error(
        "Unhandled exception on %s %s: %s\n%s",
        request.method,
        request.url.path,
        exc,
        traceback.format_exc(),
    )
    return JSONResponse(
        status_code=500,
        content={"detail": "Internal server error"},
    )
```

**Why this works:** In Starlette/FastAPI, re-raising inside an exception handler causes the exception to bubble up to the next handler in the chain. FastAPI has a built-in handler for `HTTPException` that returns the correct status code and detail. The response then flows through CORSMiddleware, which adds CORS headers.

**Also add `HTTPException` to the import at the top of the file** (line 11 already imports from `fastapi`, just add `HTTPException` to that import):

Change line 11 from:
```python
from fastapi import FastAPI, Request
```
to:
```python
from fastapi import FastAPI, HTTPException, Request
```

This ensures the `isinstance` check works correctly.

The second potential cause of 500 errors: the `GroupJoinRequest` table or `group_join_requests` table may not exist in the database the app is connected to. The `list_admin_groups` function queries `GroupJoinRequest` for pending counts (line 91-98 of `group_service.py`). If this table is missing, SQLAlchemy throws a `ProgrammingError`, which the global handler catches and returns 500.

**Step 1: Identify which database the app is connecting to.**

The `session.py` tries Neon first, falls back to local PostgreSQL. Check the backend terminal output when the app starts — it logs "Connected to Neon (primary)" or "Connected to Local PostgreSQL".

**Step 2: Run alembic migrations on the correct database.**

If connected to Neon:
```bash
cd backend
alembic upgrade head
```

If connected to local PostgreSQL:
```bash
cd backend
set DATABASE_URL=postgresql://postgres:7410@localhost:5432/expert_decision
alembic upgrade head
```

**Step 3: Verify tables exist.**

Connect to the database and check:
```sql
SELECT table_name FROM information_schema.tables 
WHERE table_name IN ('groups', 'group_memberships', 'group_join_requests');
```

All three tables must exist. If `group_join_requests` is missing, that's the cause of the 500.

**Step 4: If tables exist but enum type is missing, create it manually.**

The `group_join_requests` table uses a PostgreSQL enum type `group_join_request_status`. If the table exists but the enum is missing, queries will fail. Create it:
```sql
DO $$ BEGIN
    CREATE TYPE group_join_request_status AS ENUM ('pending', 'accepted', 'rejected');
EXCEPTION
    WHEN duplicate_object THEN null;
END $$;
```

**Step 5: Restart the backend and test.**

After ensuring tables exist, restart uvicorn and test the endpoints again.
